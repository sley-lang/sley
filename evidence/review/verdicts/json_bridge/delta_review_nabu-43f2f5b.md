## Independently re-derived claims

1. **Byte ceiling is derived, not invented.** `MAX_JSON_TEXT_BYTES = 4 * (MAX_FRAME_BYTES as usize)` (lib.rs:33) with `MAX_FRAME_BYTES = 67_108_864` imported from `sley_protocol` (lib.rs:20; protocol lib.rs:39; SMP1.md line 95 "absolute 67,108,864-byte ceiling"). 4 × 67,108,864 = 268,435,456, which equals the spec §3 literal (line 164) and the oracle's `MAX_TEXT_BYTES` (its comment now states `4 * 67_108_864`). `43f2f5b` adds `const _: () = assert!(MAX_FRAME_BYTES <= (u32::MAX as u64) / 4)` so the `u64 → usize` cast and the ×4 cannot overflow on any 32-bit-`usize` target, and `7718391` adds `const _: () = assert!(MAX_JSON_ELEMENTS <= MAX_JSON_TEXT_BYTES)`. The relationship is compiler-checked as the spec claims. The multiplier 4 is a design margin (hex doubles bodies; names and envelope need the rest) and the spec states that rationale rather than presenting 4 as a protocol constant.
2. **Element ceiling is bounded relative to a protocol limit and disclosed as such.** `MAX_JSON_ELEMENTS = 1_048_576` (lib.rs:44) is a chosen 2^20, justified against the codec's `MAX_HELLO_LIST = 4_096` (protocol lib.rs:76, enforced in `Hello` validation lines 737–746, "hello lists capped at 4,096" in spec §3). The spec does not claim it is derived from a protocol constant; it claims it bounds materialization "orders of magnitude" above any legitimate text and that "open-list length stays the frozen codec's rule … so the length rule keeps its single owner". `check_resources` (lib.rs:430–467) is an allocation-free byte scan counting `{ [ , :` outside strings; it decides nothing about protocol content. The Python oracle's `check_resources` mirrors the same scan and threshold (delta diff), so the two readers agree on the boundary.
3. **Every judgment still comes from `crates/sley-protocol`.** The hello header rule: `frame_from_value_with` (lib.rs:842–851) applies only the bridge's own all-zero-bounds shape rule, then calls `frame.validate_header()?`, which is `validate_for_version(PROTOCOL_VERSION)` in the codec (protocol lib.rs:1147–1203) — the codec compares `protocol_version` against the expected version and checks session/request-id/method/flags for hellos. The bridge holds no version comparison, no list-length rule, no method-semantics: version-aware paths delegate to `decode_frame_for_version`, `encode_frame_for_version`, `Method::V2_ALL`, `Method::from_tag_versioned`. `BridgeError::envelope` (lib.rs:156–163) fills the codec's `ProtocolFailure` record with the bridge's own code/symbol only. `frame_from_json` re-encodes through the codec so a wire-invalid frame carries `PROTOCOL_*`. So the hello-version rule added in `d384f0f` duplicates no server logic: the delta added one test (`tests.rs`, `protocol_version: 99` → `Err(BridgeError::Protocol(_))`) and a wording change; no bridge code moved for it.
4. **v1 frozen, v2 additive.** `conformance/smp1-json-bridge/v1` unchanged across the delta (empty diff); `METHOD_TABLE_JSON`, `frame_to_json`, `frame_from_json`, `hello_to_json` defaults unchanged; the checker still pins v1 41/37 and v2 43/39 with additions exactly `{306, 307}`; the oracle (41 methods, 5 vectors, 36 rejections) and the table tests pass at HEAD.
