## Independently re-derived claims

1. **Text ceiling.** `4 * 67,108,864 = 268,435,456`, equal to the revision-8 literal and to the oracle's `MAX_TEXT_BYTES`; the `43f2f5b` const assertion `MAX_FRAME_BYTES <= u32::MAX / 4` (67,108,864 <= 1,073,741,823) makes the `as usize` cast and the 4x product non-truncating on 32-bit targets at compile time. `MAX_JSON_ELEMENTS <= MAX_JSON_TEXT_BYTES` is also const-asserted.
2. **Enforced before allocation and before any frame judgment.** Every public reader (`frame_from_json`, `frame_from_json_for_version`, `hello_from_json`, `failure_from_json`, `chunk_from_json`) goes through `parse()` (lib.rs:474-476), which calls `check_resources` before `serde_json::from_str`; the only other `from_str` is the embedded trusted method table at init. `check_resources` is a single allocation-free pass over `text.bytes()` (byte length first, then depth and positions in one loop) and returns `JSON_BRIDGE_RESOURCE_LIMIT` before any `Value` exists, so no shape, encoding, or codec judgment can precede it. In the CLI the line buffer itself is bounded to `MAX_JSON_TEXT_BYTES + 2` before the bridge sees it.
3. **Element rule is safe in the overcount direction.** By induction on the tree: a scalar has V=1, P=0; an array of k>=1 children has V-P = 1 + sum(V_i-P_i) - k <= 1; an object of k pairs has V-P = 1 + k - 2k + sum(V_i-P_i) <= 1; empty containers give V-P = 0. So materialized values <= positions + 1 for every valid JSON text, and the scan never undercounts for valid JSON (string/escape tracking mirrors the JSON lexer; invalid texts fail in `serde_json` at the first error with no further materialization). Keys are counted through the `:` position. The empirical run above agrees.
4. **Tests drive each refusal.** Text too large: `tests.rs:589-592` (`frame_from_json` on `MAX_JSON_TEXT_BYTES + 1` spaces -> `ResourceLimit`; exactly the ceiling passes `check_resources`). Too deep: `tests.rs:331-340` matrix case `depth-above-ceiling` through `frame_from_json` and the v1 corpus (`rejected.json` mutation `depth-above-ceiling`, exercised by the oracle); `MAX_JSON_DEPTH` exactly passes. Too many elements: `tests.rs:612-621` (`MAX_JSON_ELEMENTS - 1` zeros pass, `MAX_JSON_ELEMENTS` zeros refused by both `check_resources` and `frame_from_json`), structural bytes inside strings count for nothing (623). Hello-version mismatch: `tests.rs:524-528` (`protocol_version` 99 on a hello -> `BridgeError::Protocol(_)`); a non-hello `protocol_version` 2 case in the matrix and the v1 corpus (`protocol-version-unsupported`) already pins `PROTOCOL_VERSION_UNSUPPORTED`. Duplicate keys last-wins: `tests.rs:627-636`.
