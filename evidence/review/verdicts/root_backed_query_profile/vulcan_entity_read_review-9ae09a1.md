### What holds (implementation)

- **Owner check order** (`crates/sley-query/src/entity_read.rs:400-464, 640-675`) matches section 4: positive-limit check (NotCanonical) -> selected-ceiling range (BudgetExceeded) -> `expected_root` (31008) -> tombstone/binding resolution (31004) -> kind (31010) -> per-object byte/K/B/work bounds -> relationship checks (31007) -> final work -> exact body length vs request and selected ceilings -> standalone ceiling. Zero-vs-over and zero-vs-wrong-root competitions are pinned (`admit_orders_zero_ceiling_before_over_selected_ceiling`, `zero_ceilings_are_not_canonical_before_root_checks`).
- **Two-phase ordering** is enforced by types, not discipline: `prepare_entity_read` returns a borrowed `EntityReadSelection<'a>` (views only, no byte copy); `server.rs:1136-1189` runs `frame_total_len` + wire ceiling, then `checked_sub(work-1)` reservation, then `capture_entity_read_selection` (first `to_vec`), then encode; a post-reservation capture/encode failure retains the full debit (`entity_read_budget_debit_table_is_exact`, `repair_debit_phases_observe_budget_and_followup`). The borrow pins capture to the same revision the selection resolved against; `plan_captures_immutable_inputs` and `selection_borrows_selected_bytes_and_captures_only_at_capture` (pointer-equality) pin it.
- **Resource soundness:** all arithmetic is checked (`work_bound`, `checked_sum`, `sized_len`); parameter count+1 vs `max_objects` refuses before `indices.reserve`; `MAX_BYTE_PAYLOAD` per object; `lookup_cost` = bit_length(N)+1 including N=0; reservation cannot underflow because `check_work` already bounded `work <= budget_before_dispatch`.
- **Adapter** (`crates/sley-repo/src/entity_read.rs`) only projects identity/kind/object_id/epoch/bytes plus Function parameter list and Parameter back-link; `VerifiedRevision::objects()` is documented and constructed in binding order (`sley-txn/src/repository.rs:1149-1150`) and `decode_bindings` (`sley-state-root/src/lib.rs:540-567`) enforces strictly sorted keys, so the owner's `binary_search_by_key` precondition is a verified invariant, and `agree` closes the gap fail-closed.
- **Poison/boundary tests** (`non_selected_bodies_are_never_semantically_extracted`, `oversized_*`, `checked_overflow_is_budget_exceeded`, `exact_and_one_below_response_and_work_limits`) are real: the owner test walks the byte ceiling down because the charged work rides inside field 8, which is the correct handling of the M-dependent body length.
- **Accepted corpus:** 23 cases, 21 `ver_*` covering all 18 kinds, `sig_multi` (generics, Option/Tuple types, effects, contracts, non-monotonic declaration order 0609 before 0602) and `sig_zero`. The Rust owner test reproduces body bytes, work, and K for all 23 from the frozen files via `include_str!`. SHA256SUMS matches all three JSON files; `inputs_sha256` is a canonical-JSON hash (not file bytes), so its difference from SHA256SUMS is by design.

### Defect found (record)

`conformance/entity-read/v2/rejected.json` row `bound_bytes_below` (`ceiling_m` 606, expected `PROTOCOL_LIMIT_EXCEEDED`) asserts a rejection that neither the Rust owner nor the oracle's own builder produces. For `ver_ws` (K=1, L=10, B=345): at M=606 the work is 1307, whose uvar is 2 bytes instead of the 3 bytes at M=200000, so the body is 606 bytes and `606 > 606` is false at `entity_read.rs:447`; the request is served. The true one-below refusal is M=605. `derive_relation` (`entity_read.py:2848-2849`) sets `ceiling_m = base_body_len - 1` from the base body at M=200000 and `check_relation` (`:2902-2905`) only re-verifies that subtraction; the rejection claim itself is never rebuilt at the new M. The runtime test `repair_response_body_ceiling_tracks_work_feedback` (`server_tests.rs:4532-4583`) explicitly documents this feedback and descends to the live threshold, so the corpus contradicts pinned runtime behaviour, and no Rust gate reads rejected vectors, so nothing would catch it.
