## Per-item adversarial analysis

**Can a second-host attestation be forged?** Yes, trivially, by construction: an attestation is an unsigned JSON object with no host binding (contract section 1 and ADR-0040 decision 5 forbid identity in it), and `validate_attestation` checks shape only. One host can run `--emit-attestation --host-label secondary` and then `--attest` that file against its own `primary`; the resulting report is byte-identical to a genuine lab reproduction, which is exactly what `evidence/release/reproducibility-report.json` looks like today (two attestations differing only in the label). The contract's trust root is operator custody of the transfer (section 5.1 step 3, "by any means the operator authorizes"), so this is a designed property, not a code defect. What is missing is the auditable lane record that would let a reviewer distinguish the two cases without putting identity in the report: the lab lane for `7a94a4a` is recorded only in the `6a2eef7` commit message, one row of the 2026-09-15 handoff table, and the RESUME procedure; the S20-730 closeout audit predates it and does not record any dual-host mint. Finding 4 (P3, record).

**Replay against a different digest or commit?** Closed by the mechanics. The attestation binds `commit` and `artifact_sha256` together; `build_report` groups by commit and raises `ATTESTATION_CONFLICT` on a digest disagreement within a commit; a replayed attestation for an older commit merges as a second commit entry (one host each, so `SINGLE_HOST_REPRODUCIBLE`) and `history_problems` flags it `stale` if any surface file moved, or `attestation-not-in-history` if it is off-branch. `MANIFEST.json` embeds the commit hex, so even a records-only re-mint rotates the digest and demotes to single-host until the lab re-attests the new commit: honest, if operationally heavy (non-actionable observation). Same-label replay collides (`duplicate host label`). `carried_attestations` fails closed on a non-report or malformed tracked file.

**Merged while dirty or unreproduced?** `working_tree_clean` must be exactly `True`, `reproducibility` exactly `REPRODUCIBLE`, `differing_members` exactly `[]`, evidence `result` exactly `PASS`; `git_state()` uses whole-tree `git status --porcelain` (untracked included, ignored excluded), and no ignored path can affect a build (`.gitignore` covers targets, dist, runtime evidence, caches, secrets only). The evidence record is gitignored and trusted as-is, which again reduces to operator custody; the primary link is confirmed by direct inspection this round.

**Can the staleness predicate be evaded?** Yes, in one latent way. `ARTIFACT_INPUT_PATHS` is meant to be "every tracked input the staged artifact derives from", but the release binary embeds two tracked files at compile time from outside the tuple: `docs/spec/SSMC1_EPOCH1_SCHEMA.txt` (`sley-schema`, `pub const SSMC1_EPOCH1_MANIFEST`, hashed at runtime) and `conformance/smp1-json-bridge/v2/methods.json` (`sley-json-bridge`, `pub const METHOD_TABLE_V2_JSON`, served on the v2 protocol branch). Both crates link into `sley-cli`. A commit that changes either file changes `bin/sley` while `git diff ... -- <surface>` stays empty, so the report reads current for an artifact the tree no longer builds, which is precisely the failure section 2 promises to prevent. It is latent (neither file changed since `7a94a4a`; last changes 2026-08-27 and 2026-09-08) and partially back-stopped elsewhere (records-closure would mark both paths ineligible; the conformance report `--check` drifts on the `methods.json` change; a unit test pins the schema's BLAKE3), but S20-730's own gate is silent, and nothing tests that embedded inputs lie inside the surface.
