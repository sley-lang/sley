### Findings

**F1 (P2, implementation)** `crates/sley-query/src/entity_read.rs:372-395`. The repair moved the object-byte copy (`view.stored_bytes.to_vec()`, total B bytes) into `prepare_entity_read`. That copy now precedes both the frame-size preflight and the `work_units - 1` reservation, which the protocol caller runs *after* `prepare_verified_entity_read` returns (`crates/sley-protocol/src/server.rs:1135-1179`). `ENTITY_READ_PROFILE_V2.md` §5 orders: body ceiling, then frame ceiling, then "No object-sized output allocation occurs before its byte ceiling is established" and "No output allocation may precede the reservation." Pre-repair (`cd64f01`) the plan borrowed the revision (`EntityReadPlan<'rev>` with `indices: Vec<usize>`), so nothing object-sized was allocated before those two gates. `LimitProfile::validate` does not require `max_frame_bytes >= max_response_bytes` (lib.rs:253-274), so a negotiated small frame ceiling with a large response ceiling makes the copy-then-refuse path reachable. Impact is bounded (copy ≤ min(request, negotiated `max_response_bytes`, `MAX_STANDALONE_BYTES`), no wrong bytes, no debit error), but it is a contract-order deviation introduced by this delta, and the commit message's "copied after every check, preserving refuse-before-result-allocation" overstates it: the frame check and the reservation are not among the checks that precede the copy. Not an S20-250 breach; an S20-310 §5 regression. Suggested repair shape: either a two-phase plan (prepare returns a borrowing/index plan; caller runs frame preflight and reservation; a `capture` or `encode` step copies afterwards) or a caller-supplied frame-derived body cap checked before capture. Either keeps the immutability property `plan_captures_immutable_inputs` proves.

**F2 (P3, record)** `crates/sley-protocol/src/server.rs:1112-1115, 1154-1157`. Doc comment and inline comment state the frame size is established "before any reservation or output allocation." True at `cd64f01`, no longer true after 7169639 for the plan's captured bytes. Stale statement in the tree that the S20-250 repair should have updated or rendered true again (resolves with F1).

**F3 (P3, record)** `scripts/check_complete_entity_impact_profile.py:209-212`. The dependency-direction check is a substring scan of `crates/sley-query/Cargo.toml` only. It cannot detect a transitive `sley-mutate` edge re-entering through `sley-check`, `sley-state-root`, or `sley-schema`, and it does not read `Cargo.lock`. Pre-existing limitation, not introduced by the repair, but it means the checker PASS claimed in 7169639 is weaker evidence for the §6 sentence than the commit message implies. Transitive closure was verified by hand above; a `Cargo.lock` closure check would make the guarantee mechanical.

**F4 (P4, implementation)** `crates/sley-query/src/entity_read.rs:162-165`. `EntityReadBody::Other { kind }` duplicates `EntityReadObject.kind`; the owner never reads the inner value. Harmless redundancy on the view surface. Consider a unit `Other` variant.

**F5 (P4, implementation)** `object_at` is evaluated up to three times for the target index and twice per parameter index (selection, `response_list_len`, capture). Each projection is O(1) and touches only selected indices, so the boundary holds; noted only as a minor inefficiency, no contract effect.

No record defects found in 733d2fa: test-inventory delta (sley-repo 386→388) matches the two new adapter projection tests at `crates/sley-repo/src/entity_read.rs:244` and `:333`; dossier state unchanged, consistent with `complete_entity_impact_profile.status = S20_250_FULL_IMPLEMENTED_REVIEW_PENDING` and all three reviews `PENDING`.
