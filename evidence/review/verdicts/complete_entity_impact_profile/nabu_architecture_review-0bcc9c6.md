### Findings (none report-grade)

- **P4 implementation** `crates/sley-query/src/entity_read.rs:434-444, 216-227`. The selection holds `Vec<EntityReadObject>` (about 168 bytes per selected object) rather than the pre-repair `Vec<usize>` (8 bytes). This is metadata, not object-sized output, bounded by admitted `max_objects` (worst case about 11 MB at 65,535), and the held views are what make capture re-resolution-free. Acceptable trade; noting it because the frame preflight follows this allocation. No contract effect.
- **P4 implementation** `crates/sley-query/src/entity_read.rs:290-298`. `EntityReadSelection::views()` is `pub` but documented "test and audit access only". The in-module test can read the private field directly; a `pub(crate)` or `#[cfg(test)]` accessor would keep the public selection surface opaque like the plan's. No capability leak, since the caller already holds the revision.
- **P4 record** `scripts/check_complete_entity_impact_profile.py:119-147`. `Cargo.lock` folds dev- and build-dependencies into `dependencies`, so the closure over-approximates: a future dev-dependency of `sley-check`, `sley-state-root`, `sley-schema`, or `sley-scb1` on `sley-mutate` would trip the guard with a message naming a transitive normal edge that does not exist. Fail-closed direction, so correct as a gate; the message would mislead.
- **P4 record** `docs/audits/S20_250_FULL_ENTITY_BODIES_CLOSEOUT.md:42`, `docs/adr/ADR-0026-complete-entity-model-boundary.md` decision 6. Neither the closeout nor the ADR records that the boundary was breached after closeout by AT-MW-02 and restored at 7169639, nor that the checker now binds the transitive closure. Lineage only; the machine-summary review note carries it.
- **P4 record** commit `0bcc9c6` bundles the REQ-01, REQ-02, and REQ-03 repairs across 33 files. Greyforge git policy asks for one coherent change set per commit; the REQ-01 delta had to be isolated by path here. No repair requested (no history rewrite without operator instruction); future rounds should commit per REQ.

Ariadne's F4 (`Other { kind }` duplication) and F5 (`object_at` evaluated up to three times per target index) remain as recorded and remain P4.

Capability-placement note, not a finding: the crate-layering invariant is enforced by one package's checker. That is adequate now that it runs in `make quick` and reads the lock, and it is what caught the AT-MW-02 breach once it was run. A workspace-level layering assertion would be the natural home if a second crate boundary ever needs the same guard.
