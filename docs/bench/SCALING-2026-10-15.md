# Scaling evidence: unrelated identity functions

Loading, projection and validation grow with program size in this experiment.
Repeated calls to one already lowered identity function remain near 2.8 µs.
The focused view stays 316 bytes while its command latency grows. Bounded output
and cached execution therefore do not establish constant-cost commands.

This is initial, narrowly scoped evidence for issue #21, finding 9. It is not an
adoption benchmark or a claim about arbitrary repositories. Source, phase
definitions and reproduction commands are in [SCALING-PHASES.md](SCALING-PHASES.md).
[Every sample and the manifest](../../bench/results/scaling-2026-10-15/) are retained.

The source base was `4bc03e2c733255d0c7a744a2691d98691806abab` (2.1.1), with
the added probe and runner hashed in the manifest. Production source was
unchanged. These are native GNU release-profile builds, not the published musl
archive: Rust 1.93.0, one build job, one codegen unit, no incremental compilation.
The host was a shared AMD Ryzen 5 3600 Linux workstation with other workloads
active. Measurements were restricted to one CPU, without exclusive core or
frequency control. Five fresh processes per size ran in a fixed shuffled order;
the OS filesystem cache was warm. No cache dropping, root installation, network
calls or native-supervisor execution took place.

Each accepted program contains `n` identity functions and `3n` objects. The
target is always `target(x: i64) -> i64`, returning `x`. The same 952-byte,
three-operation candidate changes the target to return `7` at every size.
All 20 samples verified function counts, target identity preservation, unchanged
other accepted objects, `target(42) = 42` for 101 calls, candidate validity,
`target(42) = 7` in the proposed state, and an unchanged accepted head. All 20
separate CLI calls returned `42`; all focused views selected only the target.

processes. Repeated-call values are each process's median over 100 calls, then
the median and range across those five process medians. These are observed
ranges, not confidence intervals.

The empty-process baseline medians were 2.83–3.03 ms across the four groups;
individual samples ranged from 2.01 to 16.45 ms. This includes launch, startup,
minimal output and shutdown, not isolated loader time. No baseline subtraction
was performed. The raw summary includes every measured phase and its range,
including accepted-program indexing, name loading/indexing, typed decoding,
first call, candidate loading and proposed-program indexing. Memory snapshots
include RSS and the process high-water mark at each recorded boundary.

The fixed target has no calls, branches, operations or type-graph complexity.
Unused functions, a single accepted commit, and one small edit isolate only one
axis of growth. More complex bodies, dependency graphs, histories, test sets,
storage devices and cold filesystem caches need separate measurements. The
process-memory figures are total RSS on this host; they are not allocation
counts or portable memory ceilings. The probe's post-timing fixture checks add
work to its total process duration, and its phases are not a decomposition of
the CLI's different selection/cloning path.

The run completed without failed runtime samples. A one-function pilot and an
earlier twenty-sample campaign were kept separately and excluded. After two
Clippy style fixes, this second campaign
used the final measured source and binary. Both campaigns showed the same
qualitative pattern. An initial toolchain observer ran outside the checkout;
its default Rust version was corrected to the project-pinned 1.93.0 actually used.
The source and runner received independent review, and the runner's four bounded-capture
tests passed. This evidence qualifies the cached-call claim; it does not close
the broader audit or establish all program-size effects.
