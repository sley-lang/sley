## v11 amendment: cargo fmt gate, tool provisioning, and latent implementation-gate drift

Design: `s20-530-v11-cargo-fmt-gate-amendment-design.md`. All v11 development
was done in scratch copies (a detached worktree for source-only checks, a full
clone with the repository's exact `.git/config` for git-authority checks); the
main tree stayed at `7d84433` until the reviewed amendment was ported.

Findings that shaped the amendment, in discovery order:

1. All 1929 rustfmt hunks lie inside the three owner `#[cfg(test)] mod tests`
   modules; production code, test-only items outside the modules, and every
   other crate are rustfmt-clean. No stable rustfmt configuration accepts the
   committed layout (measured: 1,997 to 4,270 hunks, spreading into every
   crate). Reformatting the modules (44,251 insertions, 11,038 deletions)
   inserts trailing commas and reorders imports, so the checker's
   token-normalized exact renderings (snapshot type aliases, grouped M2
   adapter signatures, recovery-provenance assertion statements) all break.
   Decision: exempt the checker-rendered modules with one `#[rustfmt::skip]`
   line each and let the checker accept that exact chain from a frozen
   two-element set. `cargo fmt --all -- --check` passes with zero hunks.
2. The runner tool manifest and `create_tool_bin` gain rustup-resolved
   `cargo-fmt` and `rustfmt`; the frozen `EXECUTION_TOOL_NAMES` names them.
   The sanitized runner self-test passes with the new manifest.
3. Smoking the never-executed implementation-complete path
   (`require_public_recovery_api` and the `require_implementation` row loop)
   found latent drift that would have failed the final checker after any
   passing closeout:
   - `recovery_receipt_metadata` body: frozen match-guard form (`39a6296`,
     2026-08-28) versus the `if`-in-`Ok`-arm form of the implementation
     commit (`691e870`, 2026-08-29); identical semantics. The source body is restored to the frozen
     form; the re-harvested partition shows counts, complete manifests,
     inventories, and static-pass sets unchanged, so the restoration does not
     move the reviewed v8 frontier.
   - `RecoveryAncestryError` trait check received the `production_rust`
     projection, which blanks string literals, so the `Display::fmt`
     expectation could never match; the check now receives the
     byte-preserving `normal_build_source` projection.
   - The `recover_gc_witness` signature regex demanded the explicit
     `Result<GcWitnessRecoveryStatus, GcError>` spelling while `gc.rs` has
     always used its `type Result<T> = core::result::Result<T, GcError>;`
     alias, on which the public API baseline is anchored; the checker now
     requires that exact alias at top level and accepts either spelling.
   - `limit_events_problem` rejected any `UNRESOLVED` control value or
     callable, contradicting the v5 to v8 exception partition that records
     exactly those static-resolver frontier cases as reviewed manual
     exceptions (1,666 across seven atom kinds in the committed plan, every one
     matched by `unresolved_record_sha256`; the unchanged main tree fails
     identically).
     It now accepts an unresolved entry only when its canonical digest is a
     ledgered `UNRESOLVED_BY_V8_STATIC_RESOLVER` record; hostile controls
     keep the strict default and frozen-partition equality is enforced
     separately.
4. Harness-tracked background shells were externally stopped twice during the
   v11 experiments (both limit-event attribution probes at once, about
   03:10Z). The operator confirmed on 2026-09-01 that earlier stops were not
   deliberate; the probes were relaunched detached and the stop is recorded
   here rather than treated as intent.
